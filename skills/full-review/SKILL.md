# Full Review

주기적 전면 리뷰(단일 diff 리뷰가 아니라 코드베이스/브랜치 전체 점검)를 매번 축을 새로 짜지 않고 재현 가능하게 돌리기 위한 스킬. 이음길 프로젝트에서 6축 리뷰를 4번(3회 6축 + 1회 8축·2단 중첩) 반복하며 매번 축 정의·서브에이전트 분할·결과 병합 방식을 재구성했던 비효율을 없애는 게 목적.

## 언제 쓰나

- 큰 기능/브랜치가 머지되는 시점 (가장 이상적 — 사후가 아니라 게이트로)
- 사용자가 "전체 코드 리뷰", "전면 리뷰", "지금까지 한거 점검" 같은 걸 요청할 때
- 발표/제출 전 최종 점검

단일 파일이나 단일 diff 리뷰엔 쓰지 않는다 — 그건 `requesting-code-review` 류의 가벼운 스킬로 충분하다.

## 절차

### 1. 리뷰 축 정하기

기본 축 세트(프로젝트 성격에 맞게 추가/제거):

```
- 백엔드 설계·동시성
- 백엔드 테스트 품질
- 프론트 구조·상태관리
- 보안(키 관리·인가·XSS·레이트리밋)
- 외부 연동(API 계약, 캐싱, 실패 처리)
- 문서-코드 정합성
- 운영/배포(CI, 스키마 재현, 환경변수)
```

축이 6~8개를 넘으면 하위로 쪼개지 말고 상위 병렬도를 유지한다 — 2단 중첩(축 안에서 또 서브에이전트를 뿌리는 것)은 추적성이 급격히 떨어지고, 중단 시 유실 단위가 커진다. 정말 필요하면 하되, 다음 단계(각 층 결과 즉시 파일화)를 반드시 지킨다.

### 2. 축마다 서브에이전트 병렬 파견

각 서브에이전트에게 줄 것:
- 이 축이 봐야 할 범위(디렉토리/도메인)
- "지적할 게 없으면 없다고 써라" — 억지로 findings 만들지 않게
- 심각도 기준: 🔴 BLOCKER(배포/보안 사고급) · 🟠 HIGH(기능 깨짐) · 🟡 MED(개선) · ⚪ LOW(스타일/정리)
- **출력은 파일로 저장하게 한다.** 대화 응답으로만 받지 않는다 — 세션이 죽거나 컴퓨터가 꺼지면 파일에 안 떨어진 결과는 사라진다(실제로 이 프로젝트에서 4차 리뷰 중 컴퓨터가 꺼져 서브에이전트 2개 결과가 유실된 사고가 있었음). 각 에이전트가 끝나는 즉시 `REVIEW_<축이름>.md` 같은 파일에 쓰게 하라.

### 3. 병합

각 축 파일을 읽어 하나의 문서로 합친다:
- 심각도별로 재정렬(BLOCKER 먼저)
- 중복 지적(여러 축이 같은 파일을 다른 이유로 지적) 통합
- 리뷰어 주장은 그대로 안 믿는다 — 특히 "404다", "미구현이다" 같은 단정은 실제 코드/실API를 직접 확인해 오탐 걸러낸다(이 프로젝트에서 실제로 오탐 2건을 이렇게 기각했음)

### 4. 산출물 분리

- 팀 공유용 문서(REVIEW.md 류)와 개인 스크래치를 처음부터 구분해서 만든다. §8(지식 전파)과 연결 — 확정된 발견은 팀 문서로 승격 제안한다.
- 사후 발견에서 끝내지 않는다: 가능하면 이 절차를 **머지 게이트**(자동 lint/build/test 통과 후에만 머지)와 짝지어서, 전면 리뷰는 버그잡기가 아니라 방향점검용으로 격하시키는 게 이상적이다.

## 실패 사례 (교훈)

- 위임을 2단으로 중첩하면 "어느 하위가 무엇을 봤는지" 추적이 안 되고, 중단 시 유실 단위가 커진다. 축이 늘어야 하면 상위 병렬도를 늘리고, 하위 재분할은 최후의 수단으로.
- 리뷰가 유일한 게이트면 매번 규모가 커진다 — 자동 게이트가 앞단에 있으면 전면 리뷰는 가볍게 유지된다.
